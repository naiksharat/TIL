## 1/1/2026 - Reframing & the Inverse Perspective

Say you want to bump your success rate from 99% to 99.9%.

**The optimistic take:**
99.9% - 99% = 0.9% increase. Barely anything, right? Should be a piece of cake.

**The reality check (inverse perspective):**
- 99% success = 1% failure
- 99.9% success = 0.1% failure

Going from 1% to 0.1% failure? That's a **10x improvement**. From 1% to 0.01%? A **100x improvement**.

Turns out these "tiny" gains are brutally hard to achieve. They cost a ton and take forever.

This is basically the **80/20 rule** in action. You can nail 80% of something with just 20% of the effort. But squeezing out that last 20%? Yeah, that'll take the other 80% of your time.

## 6/1/2026 - Agile, Scrum & XP

### Agile
A mindset and set of practices for working flexibly

Focuses on:
* Short work cycles
* Frequent feedback
* Adapting to change
* Collaboration
Delivers work in small, usable increments
Used beyond software (business, education, etc.)

Types
* Scrum
* Kanban
* XP

### Scrum
An Agile framework for managing work
Work is done in short cycles called sprints (1–4 weeks)
Uses story points to estimate effort, not time

### Fibonacci Series in Scrum Estimation

Common sequence used: 1, 2, 3, 5, 8, 13, 21
Good: Fibonacci, T shirt sizes, 2^x
Bad: 1-10

Used because:
* Encourages relative estimation - not time based
    * Person A with context needs 2 days
    * Person B with no context needs 4 days
    * Person A was assigned to the task, but they go on a vacation
    * Person B picks it up. They'll be under pressure to finish the task in 2 days. If not, Person B speaks and says it's gonna take 4 days.
    * Now the entire sprint planning has gone in vain and need to readjust what can be delivered  
* Reflects increasing uncertainty for larger work
* Avoids false precision (e.g., 6 vs 7)
* Helps identify stories that are too large - break it down 13 = 5 + 8 or 5 + 3 + 5

Not mandatory in Scrum, just a best practice

### XP (Extreme Programming)

An Agile methodology focused on engineering excellence
Complements Scrum well

Key XP Practices:
* Test-Driven Development (TDD) – tests before code
* Pair Programming – two developers work together
* Continuous Integration – frequent code merges and tests
* Small Releases – deliver often
* Refactoring – improve code continuously
* Simple Design – build only what’s needed now
* On-site Customer – quick requirement clarification

### Scrum vs XP
Scrum: How work is managed (roles, sprints, planning)
XP: How code is written (testing, quality, practices)
Often used together for best results

## 16/1/2026 - PR Review Tips

Today I was asked for tips on how to do PR reviews by a team member. This was my response! Some of these may be specific to our team's existing workflow.

**PR Review Process:**

**Prerequisites:**
- The PR should have a description, changes made, test results, and any other information that's relevant to get the correct context

**Steps:**

1. **Understand the problem** - If the problem statement doesn't make sense, question it and seek clarity. If the problem is invalid, comment. Review the existing code to validate the problem. Get enough context needed. Most importantly, get the correct context.

2. **Think about how you would have solved the problem** - Before diving into the code, consider your own approach.

3. **Review the PR's changes** - Check if it solves the problem. All the edge cases are taken care of. Focus should be on the business logic. If the person who raised the PR and the reviewer have the complete & correct context needed, the PR's solution is most likely to match with step 2 at a high level (there are exceptions, of course). If it doesn't, comment and discuss approaches. In those cases, most probably trade-offs would be different (for example, consistency over availability vs availability over consistency).

4. **Focus on tech & meta-tech aspects** - Some examples: Array vs maps, variable names, code style, linter, readability and simplicity over complexity, efficiency, performance.

5. **Ensure enough tests** - Unit, integration, etc. are present, and they test the core functionality, not for the sake of code coverage.

6. **Security & Observability** - Security is taken care of. Observability is taken care of (or there's a plan).

7. **Provide constructive feedback** - Be specific and polite. Don't take feedback personally, and it's not a warzone.

**TL;DR:** Context matters - tech + business. Be polite.

## 20/1/2026 - Little's Law for Determining Concurrency

### Core Interpretation

Little's Law is commonly used to reason about concurrency—how many things must be in progress at the same time to sustain a given throughput.

$$\text{Concurrency} = \text{Throughput} \times \text{Latency}$$

**Where:**
- **Concurrency** ($L$) = number of in-flight requests / goroutines / RPCs / tasks
- **Throughput** ($\lambda$) = requests per second
- **Latency** ($W$) = average time a request spends in the system

### Where It's Applied

- **gRPC / HTTP services** → in-flight RPCs per endpoint
- **Worker pools** → required workers to sustain QPS
- **Thread pools** → sizing threads to avoid starvation
- **Connection pools** → minimum open connections
- **Async pipelines** → number of messages in flight
- **Streaming systems** → concurrent streams or messages

### How It's Used

**1. Estimate required concurrency**

_Example:_ "How many workers do I need to handle 1k RPS at 50 ms latency?"

$$L = 1000 \times 0.05 = 50$$

**2. Validate observed concurrency**

- Compare measured in-flight requests to $\lambda W$
- Large gaps often indicate blocking or saturation

**3. Set limits**

- Max concurrent requests
- Backpressure thresholds
- Circuit breaker caps

**4. Capacity planning**

- Predict concurrency increase when latency grows
- Understand why small latency regressions cause big concurrency spikes

**5. Multi-endpoint services**

- Apply per endpoint to get method-level concurrency
- Aggregate only using throughput-weighted latency
- Total concurrency = sum of endpoint concurrencies

### Key Constraints

- Requires steady state
- Uses average latency, not tail latency
- Breaks down during overload or unbounded queues

### One-Line Takeaway

Concurrency is not arbitrary—Little's Law tells you the minimum in-flight work required to sustain a given throughput.


## 21/1/2026 - Why Do We Set Timeouts?

Timeouts are set to make failure explicit, bounded, and survivable in distributed systems. More concretely, they exist for these reasons:

### 1. To bound waiting time (no unbounded blocking)

Networks, processes, and dependencies can fail in ways that don't return errors:

- Packet loss
- Half-open TCP connections
- Deadlocks or slow downstreams
- Partial outages

Without a timeout, a call can wait forever. A timeout guarantees: "No matter what happens, I stop waiting after X."

### 2. To protect resources

Every in-flight request consumes resources:

- A goroutine
- Memory
- A connection from a pool
- A worker/thread

Timeouts ensure these resources are eventually released. Without them, failures turn into resource leaks, which then turn into outages.

### 3. To prevent cascading failures

Slow services are more dangerous than broken ones.

If Service B is slow:

- Service A waits
- Requests pile up
- Queues grow
- Pools exhaust
- A becomes slow or unavailable

Timeouts force fast failure, which:

- Preserves capacity
- Limits blast radius
- Keeps healthy parts of the system responsive

### 4. To enforce latency budgets and SLAs

Each service has a latency budget. Timeouts make that budget explicit:

- Client: 5s total
- Service A internal work: 1s
- Downstream call: 3s

Without timeouts, services silently exceed their budgets and violate SLAs.

### 5. To enable graceful degradation

When a timeout fires, the system can:

- Return a partial response
- Fall back to cached data
- Skip optional work
- Return a controlled error

Without timeouts, there’s no decision point—just waiting.

### 6. To improve observability and debugging

Timeouts:

- Produce clear, actionable errors (context deadline exceeded)
- Show exactly where and how long the system waited
- Make service interactions easier to reason about

Without timeouts:

- You see hung requests
- Spikes in resource usage
- No clear root cause

### 7. Because downstream guarantees don't exist

Even "reliable" services can:

- Deploy bad code
- Regress performance
- Experience GC pauses
- Hit throttling or dependency failures

Timeouts assume nothing downstream is perfectly reliable.

### Summary

Timeouts exist to bound waiting, protect resources, prevent cascading failures, enforce latency budgets, and make failures observable. In request-path calls, removing them replaces controlled failure with unbounded blocking.
